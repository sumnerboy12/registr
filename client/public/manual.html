Registr

Registr is the system of record for job identity, plus the people and clients that hang off it. Every other internal app — rostr, claimr, costr — stores only a job, person or client reference back to Registr, rather than keeping its own copy of that data. Registr is also where sign-in access to all of those apps is granted, from one place. This manual covers every screen on the main toolbar.

01

Signing in

Open Registr in a browser and you'll land on the login screen. If your organisation's Microsoft 365 identity provider is connected, a Sign in with SSO button leads — that's the everyday path. Below it, a Sign in as admin instead link reveals a password field for the break-glass login. If SSO isn't connected, that password field shows directly.

There's no self-service first account. The password field is a single hardcoded break-glass login — no username, just the password set by whoever deployed Registr (the ADMIN_PASSWORD server setting). It isn't tied to any person record, so nothing you do under People can ever affect it, and it keeps working alongside SSO as a permanent fallback.

Once you're in, your name in the top-right corner of the toolbar is itself a menu — click it for Log out.

Everyone else

Real people sign in via SSO only. Add them from the People screen (see chapter 4) and grant sign-in rights from there — see chapter 6. Nobody signs themselves up.

You can't lock yourself out

Registr won't let you revoke or demote your own admin access to Registr itself, or mark your own account inactive — one of those actions has to come from another admin.

A small badge next to the Registr name (login screen and toolbar) shows DEVELOPMENT or TEST on any deployment that isn't the real production one, so it's never mistaken for it. Nothing to do here — it's set once, server-side, when that deployment is stood up.

02

Jobs

Every job Registr tracks lives here, identified by a human code (e.g. "24-118") — the code is what other apps and people use to refer to a job, though the underlying link is always a stable internal ID, so renaming a code later doesn't break anything already pointing at it.

Type and status

Every job is either a Contract or Minor Works, and carries one status:

Tendering Awarded Active On Hold Practical Completion Closed

Registr never hard-deletes a job — Closed is how one is archived. Closed jobs drop out of the default list and search, but aren't gone; tick All statuses off the status filter, or ask for archived ones specifically, to see them again.

Working with a job

  1. Click + New Job — code and name are the only fields required up front. Site address, client, status, type, value and notes stay optional.
  2. Click any job in the list to open its detail page and edit any of those fields, including re-linking its client or changing its status.
  3. Value is free-form and independent of type — leave it blank while a job's still tendering, or whenever there isn't a fixed figure yet, but a minor works job can carry one too.

Assignments

A job's detail page also lists who's assigned to it and in what role — Project Manager, Site Supervisor, Estimator or QS. Pick a person (from active People) and a role and click Add; the same person can hold more than one role on the same job, but not the same role twice. Remove next to any row takes them off that role.

Search filters by code, name or client; the status and type dropdowns narrow the list further. The list is always sorted by code.

03

Clients

The organisations jobs are done for or through. Every client carries a type — Main Contractor, Direct or Residential — plus optional contact details and a colour.

FieldNotes
NameThe only required field.
TypeMain Contractor, Direct or Residential.
Contact name / phone / emailOptional, for the person you'd actually deal with day to day.
Accounts / payables emailOptional — kept separate from the main contact, since invoicing often goes to a different address or inbox.
ColourPicked from an 18-colour swatch, shown as a dot next to the client's name in lists.
NotesOptional free text.
ActiveTurn off instead of deleting when a client's no longer current — jobs linked to it are unaffected either way.

Inactive clients are hidden by default — tick Show inactive above the list to see them. Import pastes a client list in from a spreadsheet, Export downloads whatever's currently listed and searched — see chapter 8.

04

People

Registr's directory — everyone who might need to be assigned to a job, appear in another app, or sign in anywhere. Not everyone in People needs to sign in at all; see chapter 6 for how that's decided per person.

FieldNotes
Name / EmailBoth required, regardless of login type — an email is needed even for a None login so it's there for notifications (see chapter 6).
RoleFree text, e.g. Foreman, Estimator — distinct from a job's own assignment roles (chapter 2).
PhoneOptional.
Date of birth / Employment start & end dateOptional record-keeping fields.
Employment typeWage, Temp or Salary — a payroll/HR classification. Registr is just the master list of WRS employees; it has no bearing on whether rostr actually schedules this person, which is rostr's own separate local flag.
ColourPicked from the same 18-colour swatch as clients — used by rostr to identify this person on its Schedule.
NotesOptional free text.
ActiveTurn off instead of deleting when someone leaves — they disappear from pickers elsewhere, but their history is kept. You can't mark your own account inactive.

The search box filters by name, email or role. Inactive people are hidden by default — tick Show inactive to see them — and a second dropdown narrows the list to one employment type. Import and Export work the same way as on Clients — see chapter 8. Imported people default to the None login type (see the next chapter), since a bulk import is usually a contact list, not a batch of new logins.

05

Plant

Registr's master list of WRS-owned equipment and machinery — diggers, mixers, scaffolding, whatever you track. It mirrors People and Clients in shape, but is deliberately simpler: no type, no job or client link.

FieldNotes
NameThe only required field, e.g. "Excavator 5T".
RegoOptional registration/plate number.
ColourPicked from the same 18-colour swatch as People and Clients.
NotesOptional free text.
ActiveTurn off instead of deleting when a machine's gone from the fleet.
Owned only

Hired-in gear is deliberately not tracked here — that's a rostr-only concept, tied to a specific job and hire company, since it has no reason to be Registr master data. rostr syncs this owned list in read-only alongside it.

Inactive plant is hidden by default — tick Show inactive to see it. Import and Export work the same way as People/Clients — see chapter 8.

06

Login type & app access

Every person has exactly one login type, set on their own record — it decides whether, and how, they can sign in anywhere. Either way, an email is always required on the person's own record.

SSO

Signs in via Microsoft 365. Carries an email, which must match exactly what their identity provider signs them in with.

None

Can't sign in anywhere. Its email is used for sending schedules and other notifications, not for login.

There's no per-person local password — the only non-SSO way in is the single break-glass admin login covered in chapter 1.

Granting app access

The Access button on an SSO person's row (admin only) opens a picker with one row per app — Registr, rostr, claimr, costr — each with a role dropdown: No access, admin, editor or readonly. Changing a row takes effect immediately, no separate save step.

Your own Registr row is locked

You can grant yourself access to other apps this way, but your own Registr row is always disabled here — matching the sign-in protection in chapter 1. Have another admin change it if it's ever genuinely needed.

admin, editor and readonly mean the same thing in every app: admin can do everything editor can plus manage access/users for that app; editor can view and edit; readonly can view but not change anything.

07

API keys

rostr, claimr and costr each ask Registr, server-to-server, whether a signed-in email is allowed into that app and with what role — the same access decided in chapter 6. Each app needs its own credential to do that, managed from the API Keys screen (admin only).

  1. Click + Generate Key, pick the app, and an optional label to tell keys apart later (e.g. "production").
  2. The plaintext key is shown once, right after creating it — copy it into that app's server config immediately. Only its hash is stored in Registr, so it can't be shown again.
  3. Revoke deletes a key permanently — there's no deactivate-and-reactivate step. Generate a new one if an app needs a key again.

The list shows each key's app, label, when it was created, and when it was last used — handy for spotting one that's gone stale.

Email, too

The same key also lets an app ask Registr to send email on its behalf, using the SMTP account configured under Registr's own server settings — so rostr, claimr and costr don't need SMTP credentials of their own. Nothing to manage here beyond the key itself.

08

Importing & exporting

The People, Clients and Plant screens each have Import and Export buttons for working with a spreadsheet you already keep, instead of retyping everything by hand.

  1. Select and copy the rows in Excel or Google Sheets — include the header row — and paste the whole block into the box.
  2. Registr detects your columns and tries to auto-match them to the right fields; adjust any dropdown that guessed wrong, or set it to — Don't import — to skip a column.
  3. Check the preview of the first few rows, then click Import. Name is always required (plus email, for People) — everything else can be left unmapped.

A row matching an existing record — by email for People, by name for Clients/Plant — or an earlier row in the same paste, is skipped as a duplicate rather than re-created; the result summary counts these separately from actual failures. A row that genuinely fails (e.g. a missing required field) is listed with the reason afterwards; everything else still imports, so one bad row won't block the rest of the batch.

Export downloads a CSV of whatever's currently listed and searched — not necessarily everything, if you've filtered the list first.

Doubles as backup/restore

Export now covers every field on a record, not just the obvious ones, so re-importing the same file reproduces each person/client/plant item faithfully — that's the "restore" half. This is per-entity (People, Clients and Plant each export/import their own CSV), not one combined whole-database file, and a restored record gets a new internal ID — a person's app-access grants (chapter 6) aren't part of the export and need re-setting by hand afterwards.

09

Your data

Every job, person, client and API key lives in one SQLite database file on whichever machine hosts Registr — there's no cloud copy behind it.

Back it up

Ask whoever manages the server to back up that database file periodically. If the host machine is lost without a backup, the data goes with it — this is worth confirming with them rather than assuming it's automatic.

The Registr icon in the top-left corner of the toolbar links to the exact commit currently running, if you ever need to check whether an update has actually gone live — handy to know when reporting something that seems fixed already, or confirming a fix has actually landed.
