Registr

Registr is the system of record for job identity, plus the people and clients that hang off it. Every other internal app — rostr, claimr, costr — stores only a job, person or client reference back to Registr, rather than keeping its own copy of that data. Registr is also where sign-in access to all of those apps is granted, from one place. This manual covers every screen on the main toolbar.

01

Signing in

Open Registr in a browser and you'll land on the login screen. If your organisation's Microsoft 365 identity provider is connected, a Sign in with SSO button leads — that's the everyday path. A small Admin link, off to the side, reveals a password field for the break-glass login. If SSO isn't connected, that password field shows directly.

There's no self-service first account. The password field is a single hardcoded break-glass login — no username, just the password set by whoever deployed Registr (the ADMIN_PASSWORD server setting). It isn't tied to any person record, so nothing you do under People can ever affect it, and it keeps working alongside SSO as a permanent fallback.

Once you're in, your name in the top-right corner of the toolbar is itself a menu — click it for Log out.

Everyone else

Real people sign in via SSO only. Add them from the People screen (see chapter 4) and grant sign-in rights from there — see chapter 6. Nobody signs themselves up.

You can't lock yourself out

Registr won't let you revoke or demote your own admin access to Registr itself, or mark your own account inactive — one of those actions has to come from another admin.

A small badge next to the Registr name (login screen and toolbar) shows DEVELOPMENT or TEST on any deployment that isn't the real production one, so it's never mistaken for it. Nothing to do here — it's set once, server-side, when that deployment is stood up.

02

Jobs

Every job Registr tracks lives here, identified by a human code — the code is what other apps and people use to refer to a job. Every app and integration pointing at a job actually joins on its stable internal ID, not the code, but the code itself is locked in at creation and can't be changed afterwards (see below), so it never drifts out of sync with what's printed on paperwork, invoices, and so on.

Codes are generated automatically as YYXXX (e.g. "26001") — the year, then the next unused number that year, shared across every job type (not counted separately per type), so the number alone tells you creation order regardless of type; a Contract, a Minor Works and a Remedial job created the same year never collide on the same number. Job type is shown by a colour tint on each row in the Jobs list instead of a letter in the code. Only admins can override the suggested code, and only while creating the job.

A job's own page lives at a URL built straight from its code (e.g. /jobs/26001), so it's safe to type, bookmark or paste one into an email or another system without looking anything up first — the code being locked in for good is exactly what makes that safe to rely on.

Type and status

Every job is a Contract, Minor Works or Remedial job, and carries one status:

Tendering Awarded In Progress On Hold Practical Completion Awaiting Retentions Completed Lost

Registr never hard-deletes a job — Completed or Lost is how one is archived. Practical Completion and Awaiting Retentions are the retentions-scheme pair and only make sense on Contract jobs — they're hidden from a Minor Works or Remedial job's own Status field, and from the status filter/board unless Contract is part of the current Type selection (see "Filtering and the Board view" below).

There's no delete

A job can't be deleted from Registr, by anyone — Completed/ Lost is the only way to archive one that's done or didn't happen.

Working with a job

  1. Click + Add Job — name is the only field required up front; code is filled in for you (see above). Site address, client, contact, status, value and notes stay optional.
  2. Click any job in the list to open its detail page and edit any of those fields, including re-linking its client or changing its status — except Code, which is locked as soon as the job is created (Type can still change later, e.g. a job quoted as Minor Works that turns out to need a full Contract — the code itself doesn't change, just the colour tint shown against it).
  3. No client in the list yet? Leave Client blank and a Client name field appears — a free-text placeholder for a prospect, cleared automatically the moment you link a real client instead. A job also carries its own Contact name/Contact email, independent of the linked client's own contact details.
  4. Value is a currency field, free-form and independent of type — leave it blank while a job's still tendering, or whenever there isn't a fixed figure yet. It's hidden entirely (not just optional) on a Remedial job, since remedial work isn't billed as one fixed sum.
Code is locked once created

It can't be changed after the job is saved, by anyone — not even an admin. While still creating a new job, Editors and read-only users see the auto-filled code but can't change it — only an admin can type over the suggestion.

Assignments

A job's detail page shows who's assigned to it and in what role, as a row of compact pills — Project Manager, Site Supervisor, Estimator or QS — each linking to a mailto: for that person if they have an email on file. Click Add role to pick a person (from active People) and a role; the same person can hold more than one role on the same job, but not the same role twice. The × on any pill removes that assignment.

Comments

Each job has its own comment thread, furthest down its detail page — a running, timestamped conversation rather than a single notes field. Your own comments show tinted and right-aligned to tell them apart from everyone else's at a glance. Edit and Delete only appear on comments you posted yourself; anyone with write access can post a new one.

Attachments

+ Add under Attachments uploads a file of any kind against the job — a site photo, a signed PDF, a spreadsheet, whatever's relevant. Images get an inline thumbnail; anything else just shows its name, size, who uploaded it and when. Delete removes one.

Attachments live on disk, not in the database

Unlike everything else in Registr, attachment files are stored under data/attachments/ next to the SQLite database, not inside it. A backup that only copies registr.db misses them — back up the whole data/ folder (see chapter 10).

QA Checklist

Every job has its own checklist, summarised on a QA Checklist card on the job's own page — click anywhere on that card to open the full checklist on its own dedicated page, kept separate so a long list of items doesn't have to compete for space with the rest of the job's fields, assignments and comments.

Items are grouped into four fixed stages — Pre-Start, In Progress, Completion, Warranty — and each can be Open, In Progress, Done or Won't Do (the last two both count as finished). A stage collapses itself automatically once every item in it is finished, and reopens if an item in it is reopened or a new one is added to it. Sync template copies in any admin-maintained template item (see Checklist Templates under the admin menu) not already on the job, matched by job type — a new item added to the template later doesn't retroactively appear on existing jobs until Sync template is clicked. Export PDF opens a print-friendly one-page summary of the checklist, suitable for handing to a client or filing.

Filtering and the Board view

Search filters by code, name or client. The status filter is a multi-select checklist with All/Active/ None shortcuts (Active excludes On Hold, Completed and Lost); the type filter is three toggle buttons, Contract/Minor Works/Remedial. Both remember your last selection per browser. The list itself sorts by client name, then code.

List/Board switches between a table and a kanban board — one column per status, jobs as cards you can drag between columns to change status directly (saved immediately; a rejected change snaps the card back). Dragging a card to the board's left or right edge auto-scrolls it into view; clicking and dragging empty board space pans around instead of needing a visible scrollbar. Your last-used view, and both filters, are remembered per browser.

Importing and exporting

Import and Export work the same way as People/Clients/Plant (see chapter 9) — a row matches an existing job by code, not name. Type comes from the Type column (defaulting to Contract if it's blank or unrecognised); common status synonyms are recognised too ("Pipeline"/"Quoted" → Tendering, "Confirmed" → Awarded). The four assignment-role columns (Project Manager, Site Supervisor, Estimator, QS) match a person by name — a name that doesn't match any active person is silently skipped, same as an unmatched Client.

ThinkSafe

A ThinkSafe badge next to a job's name means that job's code has a site configured in ThinkSafe (Wayman's H&S system) — registr checks in the background every 15 minutes (this same sync also covers People's own ThinkSafe badge — see chapter 4); there's no manual refresh in the UI, so a brand-new site can take up to 15 minutes to show up. Read-only: nothing done in registr ever changes anything in ThinkSafe. Only shows up at all once whoever manages the server has set THINKSAFE_API_URL/ THINKSAFE_API_KEY — see the README.

03

Clients

The organisations jobs are done for or through. Every client carries a type — Main Contractor, Direct or Residential — plus optional contact details and a colour.

FieldNotes
NameThe only required field.
TypeMain Contractor, Direct or Residential.
Contact name / phone / emailOptional, for the person you'd actually deal with day to day.
Accounts / payables emailOptional — kept separate from the main contact, since invoicing often goes to a different address or inbox.
ColourPicked from an 18-colour swatch, shown as a dot next to the client's name in lists.
NotesOptional free text.
ActiveTurn off instead of deleting when a client's no longer current — jobs linked to it are unaffected either way.

Inactive clients are hidden by default — tick Show inactive above the list to see them. Import pastes a client list in from a spreadsheet, Export downloads whatever's currently listed and searched — see chapter 9.

04

People

Registr's directory — everyone who might need to be assigned to a job, appear in another app, or sign in anywhere. Not everyone in People needs to sign in at all; see chapter 6 for how that's decided per person.

FieldNotes
Name / EmailBoth required, regardless of login type — an email is needed even for a None login so it's there for notifications (see chapter 6).
RoleFree text, e.g. Foreman, Estimator — distinct from a job's own assignment roles (chapter 2).
PhoneOptional.
Date of birth / Employment start & end dateOptional record-keeping fields — but not purely passive: every day at 3am, Registr automatically deactivates anyone whose employment end date has passed (which also revokes their SSO access), and emails a summary to every admin with an email on file if the server's mail is configured.
Employment typeWage, Temp or Salary — a payroll/HR classification. Registr is just the master list of WRS employees; it has no bearing on whether rostr actually schedules this person, which is rostr's own separate local flag.
ColourPicked from the same 18-colour swatch as clients — used by rostr to identify this person on its Schedule.
NotesOptional free text.
ActiveTurn off instead of deleting when someone leaves — they disappear from pickers elsewhere, but their history is kept. You can't mark your own account inactive.

The search box filters by name, email or role. Inactive people are hidden by default — tick Show inactive to see them — and a second dropdown narrows the list to one employment type. Import and Export work the same way as on Clients — see chapter 9. Imported people default to the None login type (see the next chapter), since a bulk import is usually a contact list, not a batch of new logins.

ThinkSafe

A ThinkSafe badge next to a person's name means their name matches a user in ThinkSafe (Wayman's H&S system), checked case-insensitively — registr checks in the background every 15 minutes (the same sync as the Jobs screen's own ThinkSafe badge — see chapter 2); there's no manual refresh in the UI. Read-only: nothing done in registr ever changes anything in ThinkSafe. Only shows up at all once whoever manages the server has set THINKSAFE_API_URL/THINKSAFE_API_KEY — see the README.

05

Plant

Registr's master list of WRS-owned equipment and machinery — diggers, mixers, scaffolding, whatever you track. It mirrors People and Clients in shape, but is deliberately simpler: no type, no job or client link.

FieldNotes
NameThe only required field, e.g. "Excavator 5T".
RegoOptional registration/plate number.
ColourPicked from the same 18-colour swatch as People and Clients.
NotesOptional free text.
ActiveTurn off instead of deleting when a machine's gone from the fleet.
Owned only

Hired-in gear is deliberately not tracked here — that's a rostr-only concept, tied to a specific job and hire company, since it has no reason to be Registr master data. rostr syncs this owned list in read-only alongside it.

Inactive plant is hidden by default — tick Show inactive to see it. Import and Export work the same way as People/Clients — see chapter 9.

06

Login type & app access

Every person has exactly one login type, set on their own record — it decides whether, and how, they can sign in anywhere. Either way, an email is always required on the person's own record.

SSO

Signs in via Microsoft 365. Carries an email, which must match exactly what their identity provider signs them in with.

None

Can't sign in anywhere. Its email is used for sending schedules and other notifications, not for login.

There's no per-person local password — the only non-SSO way in is the single break-glass admin login covered in chapter 1.

Granting app access

The Access button on an SSO person's row (admin only) opens a picker with one row per app — Registr, rostr, claimr, costr — each with a role dropdown: No access, admin, editor or readonly. Changing a row takes effect immediately, no separate save step.

Your own Registr row is locked

You can grant yourself access to other apps this way, but your own Registr row is always disabled here — matching the sign-in protection in chapter 1. Have another admin change it if it's ever genuinely needed.

admin, editor and readonly mean the same thing in every app: admin can do everything editor can plus manage access/users for that app; editor can view and edit; readonly can view but not change anything.

07

API keys

rostr, claimr and costr each ask Registr, server-to-server, whether a signed-in email is allowed into that app and with what role — the same access decided in chapter 6. Each app needs its own credential to do that, managed from the API Keys screen (admin only).

  1. Click + Generate Key, pick the app, and an optional label to tell keys apart later (e.g. "production").
  2. The plaintext key is shown once, right after creating it — copy it into that app's server config immediately. Only its hash is stored in Registr, so it can't be shown again.
  3. Revoke deletes a key permanently — there's no deactivate-and-reactivate step. Generate a new one if an app needs a key again.

The list shows each key's app, label, when it was created, and when it was last used — handy for spotting one that's gone stale.

Email, too

The same key also lets an app ask Registr to send email on its behalf, using the SMTP account configured under Registr's own server settings — so rostr, claimr and costr don't need SMTP credentials of their own. Nothing to manage here beyond the key itself.

08

Reports

A growing menu of read-only summaries, separate from the day-to-day screens above — reachable from Reports on the main toolbar. Everyone can view them, regardless of role.

Job Value

Total job value (see chapter 2), and how many jobs make up that total, broken down by type down the columns and status along the rows — with a Total row and column. A blank cell means no jobs exist in that combination; jobs with no value set are counted (the number in brackets) but don't add to the total shown.

09

Importing & exporting

The Jobs, People, Clients and Plant screens each have Import and Export buttons for working with a spreadsheet you already keep, instead of retyping everything by hand.

  1. Select and copy the rows in Excel or Google Sheets — include the header row — and paste the whole block into the box.
  2. Registr detects your columns and tries to auto-match them to the right fields; adjust any dropdown that guessed wrong, or set it to — Don't import — to skip a column.
  3. Check the preview of the first few rows, then click Import. Name is always required (plus email, for People) — everything else can be left unmapped.

A row matching an existing record — by email for People, by name for Clients/Plant, by code for Jobs — or an earlier row in the same paste, is skipped as a duplicate rather than re-created; the result summary counts these separately from actual failures. A row that genuinely fails (e.g. a missing required field) is listed with the reason afterwards; everything else still imports, so one bad row won't block the rest of the batch. See chapter 2 for Jobs import's own quirks (code-prefix-implies-type, status synonyms, assignment columns).

Export downloads a CSV of whatever's currently listed and searched — not necessarily everything, if you've filtered the list first.

Doubles as backup/restore

Export now covers every field on a record, not just the obvious ones, so re-importing the same file reproduces each job/person/client/plant item faithfully — that's the "restore" half. This is per-entity (Jobs, People, Clients and Plant each export/import their own CSV), not one combined whole-database file, and a restored record gets a new internal ID — a person's app-access grants (chapter 6), and a job's comments/attachments, aren't part of the export and need re-setting by hand afterwards.

10

Your data

Every job, person, client and API key lives in one SQLite database file on whichever machine hosts Registr — there's no cloud copy behind it. The one exception is job attachments (see chapter 2), which live as plain files alongside that database, not inside it.

Back it up

Ask whoever manages the server to back up the whole data folder — the database file and the attachments alongside it — periodically. If the host machine is lost without a backup, the data goes with it — this is worth confirming with them rather than assuming it's automatic.

The Registr icon in the top-left corner of the toolbar links to the exact commit currently running, if you ever need to check whether an update has actually gone live — handy to know when reporting something that seems fixed already, or confirming a fix has actually landed.
